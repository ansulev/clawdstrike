**Lesson 3: Fail-Closed** (`03-fail-closed/page.mdx`)

Frontmatter:
```yaml
---
title: "Fail-Closed Design"
order: 3
track: "threat-scenarios"
description: "Why ClawdStrike denies access even when a guard throws an error"
---
```

Prose outline:

1. **The Principle**: In security engineering, "fail-closed" means that when something goes wrong, access is DENIED, not granted. The alternative (fail-open) is what most software does by default -- if the check crashes, let the action through. ClawdStrike never fails open.

2. **Why This Matters**: Imagine a guard that checks for forbidden paths. If the guard crashes (bug, OOM, unexpected input format), should the file access be allowed? In a fail-open system: yes. In ClawdStrike: no. The error itself is treated as a reason to deny.

3. **Interactive Demo**: Show two scenarios side by side:
   - Scenario A (fail-open): Guard error -> action ALLOWED -> attacker wins
   - Scenario B (fail-closed): Guard error -> action DENIED -> attacker blocked

4. **Code Example**: Show annotated Rust code demonstrating the fail-closed pattern. Use a code block (not AnnotatedSource -- there's no specific tagged region for this generic pattern):
```rust
// In ClawdStrike's engine, every guard error maps to DENY
match guard.check(&action) {
    Ok(GuardResult::Allow) => continue,  // Only explicit Allow passes
    Ok(GuardResult::Deny(reason)) => return Deny(reason),
    Err(e) => return Deny(format!("Guard error: {}", e)),  // Fail-closed!
}
```

5. **Three Levels of Fail-Closed**:
   - Guard evaluation errors -> DENY
   - Policy parse errors -> reject at load time (invalid policy never runs)
   - Configuration errors -> `deny_unknown_fields` prevents silent misconfiguration

6. **Playground**: Embed a prompt injection playground with a note that errors are treated as denials:
```mdx
<GuardPlayground guard="prompt_injection" />
```

7. **Design Pattern**: `#[must_use]` on verdict types prevents accidentally ignoring a deny result. `deny_unknown_fields` on all serde types catches YAML typos.

**Lesson 4: Enforcement Tiers** (`04-enforcement-tiers/page.mdx`)

Frontmatter:
```yaml
---
title: "Enforcement Tiers"
order: 4
track: "threat-scenarios"
description: "Three ways to deploy ClawdStrike: in-process, sidecar, and centralized"
---
```

Prose outline:

1. **Introduction**: ClawdStrike isn't one-size-fits-all. It deploys at three enforcement tiers, each with different tradeoffs between latency, isolation, and control.

2. **Tier 1: In-Process (Guards)** -- Guards run inside the agent process. Lowest latency (~microseconds). Guard pipeline evaluates actions synchronously. Best for: development, single-agent setups, latency-sensitive operations.
   - Diagram: ASCII art or styled div showing `[Agent Process [Guard Pipeline -> Action]]`
   - Tradeoffs: Fast but the agent could theoretically tamper with guards (same process). Use for trusted agent code.

3. **Tier 2: Sidecar (brokerd)** -- ClawdStrike runs as a separate local process. Agent communicates via localhost. Capability-based: agent requests a capability, brokerd validates it, injects secrets, executes upstream call. Best for: API access control, secret management.
   - Diagram: `[Agent Process] <-> [brokerd Sidecar] <-> [Upstream API]`
   - Tradeoffs: Process isolation prevents tampering. Agent never sees raw secrets. Slightly higher latency (~milliseconds).

4. **Tier 3: Centralized (hushd)** -- Remote HTTP daemon. Fleet-wide policy enforcement. Signs capabilities with Ed25519. Produces completion bundles as cryptographic proof. Best for: multi-agent, enterprise, compliance-heavy.
   - Diagram: `[Agent 1] <-> [hushd Server] <-> [Policy DB]` and `[Agent 2] <->`
   - Tradeoffs: Full audit trail, fleet-wide control. Higher latency (network round-trip). Single point of policy enforcement.

5. **Comparison Table**: Show a markdown table comparing the 3 tiers across: Latency, Isolation, Secret Handling, Audit Trail, Best For.

6. **When to Use Each**: Quick decision guide:
   - Prototyping? -> In-process
   - Production with secrets? -> Sidecar
   - Enterprise/compliance? -> Centralized

**Lesson 5: Security Regression: URL Spoofing** (`05-url-spoofing/page.mdx`)

Frontmatter:
```yaml
---
title: "Security Regression: URL Spoofing"
order: 5
track: "threat-scenarios"
description: "How a URL userinfo attack bypassed the egress guard — and how it was fixed"
---
```

Prose outline:

1. **Introduction**: Security is a cat-and-mouse game. Even well-designed guards can have blind spots. This lesson walks through a real security regression from ClawdStrike's test suite -- a URL spoofing attack that tricked the egress allowlist guard.

2. **The Attack**: RFC 3986 allows a "userinfo" component in URLs: `https://user:password@host/path`. The userinfo is everything before `@`. A clever attacker crafts: `https://api.openai.com:443@evil.example/path`. To a naive parser, the host looks like `api.openai.com`. But the REAL host is `evil.example` -- the `api.openai.com:443` part is just the userinfo.

3. **Why It Matters**: If the egress allowlist guard checks the apparent host (`api.openai.com`) instead of the real host (`evil.example`), the attacker can exfiltrate data to any domain by prepending an allowed domain as userinfo.

4. **The Vulnerable Code**: Show the concept of naive host extraction:
```rust
// VULNERABLE: naive host extraction
fn extract_host_naive(url: &str) -> &str {
    // Strips scheme, takes everything before first '/' or ':'
    // Would return "api.openai.com" for the spoofed URL!
}
```
